## 2. 배경 및 문제 정의 (Why)

**핵심 시각 자료**
- 운영자의 하루를 3단 타임라인으로 표현: 트렌드 확인 → 도매 사이트 검색 → 주문별 발주서 작성
- 각 단계에 "수작업" 빨간 태그

**슬라이드 본문**
- 소규모 패션 쇼핑몰 운영자의 반복 수작업
  - **트렌드:** 감과 SNS 눈팅에 의존, 근거 데이터 없음
  - **소싱:** 도매 사이트를 키워드마다 반복 검색, 이미지 수동 저장
  - **발주:** 주문마다 공급처별 발주서를 엑셀로 직접 작성·발송
- 문제의 본질: 같은 일을 매일 반복하고, 단계 사이 데이터가 끊겨 있음
- 목표: 세 단계를 **하나의 데이터 파이프라인**으로 연결

**발표자 스크립트**
> 소규모 쇼핑몰 운영자의 하루를 보면 세 가지 반복 작업이 있습니다.
> 첫째, 뭐가 뜨는지를 감으로 판단합니다. 둘째, 그 키워드로 도매 사이트를 하나씩 검색하고 이미지를 저장합니다. 셋째, 주문이 들어오면 공급처마다 발주서를 엑셀로 만들어 보냅니다.
> 저희가 주목한 건 이 세 작업이 서로 연결된 데이터인데도 매번 사람이 옮겨 적는다는 점이었습니다. 트렌드 키워드가 소싱 검색어가 되고, 소싱한 상품이 주문이 되고, 주문이 발주서가 됩니다. 그래서 이걸 하나의 파이프라인으로 잇는 것을 목표로 잡았습니다.

## 3. 핵심 가치 및 솔루션 (What)

**핵심 시각 자료**
- 3열 카드: ① Trend ② Sourcing ③ Order, 각 카드 아래 "전 → 후" 비교 표

**슬라이드 본문**

| 기능 | 기존 (수작업) | fashionpick |
|---|---|---|
| ① 트렌드 수집·분석 | 감 · SNS 확인 | 60분마다 자동 수집, 급상승 키워드 자동 하이라이트 |
| ② 도매 소싱·상품 등록 | 키워드별 반복 검색, 이미지 수동 저장 | 상위 키워드로 180분마다 자동 수집, 판매가·마진·상품명 추천 후 원클릭 등록 |
| ③ 발주 자동화 | 주문마다 엑셀 작성·메일 발송 | 주문 즉시 공급처별 발주서(Excel/PDF) 생성, 이메일·웹훅 발송, 실시간 알림 |

- 소요 시간 절감 수치: [확인 필요 — 실측한 값이 없으므로 "단계 수 감소"로만 표현]

**발표자 스크립트**
> 그래서 fashionpick은 세 가지를 자동화합니다.
> 트렌드는 60분마다 수집해서 급상승 키워드를 바로 보여 주고, 소싱은 상위 키워드로 180분마다 도매 상품을 모아 판매가와 마진, 상품명까지 추천해서 버튼 하나로 등록하게 했습니다. 주문이 들어오면 공급처별 발주서가 즉시 만들어지고 발송까지 이어집니다.
> 정확한 시간 절감은 실측하지 못해서 숫자로 말씀드리진 않겠습니다. 대신 운영자가 직접 하던 단계가 "확인하고 승인하는 일"로 줄어든다는 점을 강조드리고 싶습니다.

## 4. 전체 시스템 아키텍처

**핵심 시각 자료**
- 데이터 흐름도 (왼쪽 → 오른쪽)

```
[React(Vite) SPA]
  ├─ Netlify (스테이징)  fashionpick.netlify.app
  └─ Render Static (프로덕션)  fashionpick.onrender.com
        │  REST (JWT Bearer)      │  WebSocket /ws?token=
        ▼                          ▼
[FastAPI · Render Docker]  fashionpick-api.onrender.com
  ├─ routers: auth · shop · trends · catalog · orders · admin · realtime
  ├─ services: trends · catalog · ordering · rpa_jobs · realtime
  └─ asyncio 스케줄러 ─▶ 워커 스레드 ─▶ rpa/* (Playwright · Requests)
        │ SQLAlchemy (PyMySQL + TLS)           │
        ▼                                       ▼
[TiDB Cloud]                     [네이버 데이터랩 · 랭킹 페이지 · 도매 사이트 · SMTP · 웹훅]
```

**슬라이드 본문**
- 프런트·백엔드 **완전 분리**: 정적 SPA는 CDN, API는 Docker 컨테이너
- 프런트 2곳 배포: Netlify = 스테이징, Render Static = 프로덕션
- RPA 엔진은 API 프로세스 안의 **스케줄러 + 워커 스레드** (무료 티어 단일 인스턴스에 맞춤)
- 실시간 이벤트는 WebSocket 하나로 통합 (주문 · 발주 · 트렌드 · RPA)

**발표자 스크립트**
> 전체 구조입니다. 프런트는 React 정적 사이트라 Netlify와 Render Static 두 곳에 올렸고, 하나는 스테이징, 하나는 프로덕션으로 썼습니다.
> 백엔드는 FastAPI를 Docker 컨테이너로 Render에 올렸습니다. 컨테이너를 고른 이유는 RPA 때문입니다. Playwright가 쓰는 Chromium을 이미지에 같이 넣어야 했거든요.
> 제가 설계한 부분은 RPA 엔진 위치입니다. 별도 워커 서버를 두면 좋지만 무료 티어는 인스턴스가 하나라서, API 프로세스 안에 asyncio 스케줄러를 두고 무거운 수집은 워커 스레드로 돌렸습니다. 이 트레이드오프는 마지막 회고에서 다시 말씀드리겠습니다.

## 5. 기술 스택 선정 이유 (Why)

**핵심 시각 자료**
- 2열 표: 기술 / 고른 이유 / 대안과 비교

**슬라이드 본문**

| 기술 | 고른 이유 | 비교한 대안 |
|---|---|---|
| Playwright | 자바스크립트로 렌더링되는 랭킹·도매 페이지 수집, 빌드 시 Chromium을 이미지에 포함 | Requests만으로는 동적 페이지 불가 |
| FastAPI | 비동기 + WebSocket 기본 지원, `/docs` 자동 API 문서 | Flask (WebSocket 별도 구성 필요) |
| TiDB Cloud | MySQL 호환 서버리스, 무료 티어, TLS 필수 | 관리형 MySQL (비용) |
| SQLite (로컬·테스트) | 같은 SQLAlchemy 코드로 `DATABASE_URL`만 바꿔 전환, 테스트마다 임시 DB | 테스트도 클라우드 DB (느리고 운영 데이터 오염 위험) |
| Tailwind v4 | 디자인 토큰(`@theme`)과 `@utility`로 공통 규칙 관리, 다크 모드 | CSS 모듈 (토큰 공유 번거로움) |
| pandas / NumPy | 스냅샷 비교·집계를 간결하게 표현 | 순수 파이썬 반복문 |

**발표자 스크립트**
> 기술은 "이게 유명해서"가 아니라 문제에 맞춰 골랐습니다.
> 수집 대상 페이지가 자바스크립트로 그려지기 때문에 Playwright가 필요했고, 그게 Docker 배포로 이어졌습니다. FastAPI는 WebSocket을 기본으로 지원해서 실시간 알림을 같은 서버에서 처리할 수 있었습니다.
> DB는 운영은 TiDB, 로컬과 테스트는 SQLite로 나눴습니다. 코드는 그대로 두고 접속 주소만 바꾸게 만들어서, pytest는 매번 임시 SQLite로 돌고 운영 데이터는 건드리지 않습니다. 이 결정을 왜 했는지는 트러블슈팅에서 실제 사례로 말씀드리겠습니다.

## 6. 핵심 기술 ①: RPA 수집 파이프라인 (발표자 담당)

**핵심 시각 자료**
- 파이프라인 다이어그램: 스케줄러 → `trend_collect` → `product_sourcing` → upsert · 이미지 저장
- 관리자 RPA 모니터 캡처 (`/admin/rpa`: 작업 카드, 주기, 로그 표)

**슬라이드 본문**
- RPA 작업 3종 · asyncio 스케줄러가 주기마다 워커 스레드로 실행
  - `trend_collect` 60분 · `product_sourcing` 180분 · `po_dispatch` 30분
  - 같은 작업은 **동시에 한 번만** 실행 (락), 결과는 `rpa_logs`에 기록
- 트렌드 수집
  - 네이버 데이터랩 쇼핑인사이트 API + Playwright 랭킹 페이지 수집
  - 카테고리 7개 · 시드 키워드 43개
- 도매 소싱: 상위 8개 키워드로 검색 → 상품명·가격·이미지·링크 추출 → `source_url` 기준 upsert
- 크롤링 준수: robots.txt 확인, 도메인별 요청 간격 제한(기본 2초)
- `RPA_MODE=demo/live`: demo는 외부 접속 없이 전체 흐름 시연

**발표자 스크립트**
> 여기서부터 제가 직접 맡은 부분입니다.
> RPA 작업은 세 개이고, 스케줄러가 주기를 보고 워커 스레드에서 실행합니다. 같은 작업이 겹쳐 실행되면 중복 데이터가 생기기 때문에 작업 이름 단위로 락을 걸었고, 성공이든 실패든 모든 실행을 로그로 남겨서 관리자 화면에서 볼 수 있게 했습니다.
> 소싱은 같은 상품이 여러 번 수집되는 게 문제였는데, 원본 링크를 기준으로 있으면 가격과 재고만 갱신하고 없으면 새로 넣는 upsert로 처리했습니다.
> 그리고 크롤링은 수집 전에 robots.txt를 확인하고 같은 도메인에는 2초 간격을 두도록 했습니다. 외부 사이트에 부담을 주지 않는 것도 기술 요구사항이라고 생각했습니다.

## 7. 핵심 기술 ②: 트렌드 분석 · 가격 로직과 시각화 (발표자 담당)

**핵심 시각 자료**
- 수식 박스 3개 (아래 본문)
- 트렌드 페이지 캡처 (`/trends`: 워드클라우드, 검색 지수 라인 차트, 카테고리 트리맵, Top 12 바 차트)

**슬라이드 본문**
- **앵커 정규화** — 데이터랩은 요청마다 최댓값을 100으로 정규화
  - 카테고리 첫 키워드(앵커)를 매 요청에 포함
  - `점수 = (키워드 최근 7일 평균 ÷ 앵커 최근 7일 평균) × 50` (최대 100)
- **급상승 판정** — 직전 스냅샷 대비 점수 **+15% 이상** 또는 순위 **+5 이상**
- **판매가 · 마진**
  - `판매가 = ⌈도매가 × 2.2 ÷ 1,000⌉ × 1,000 − 100` (900원 엔딩)
  - 예: 39,500원 → **86,900원**, 마진율 **54.5%**
- **상품명 추천** — `[시즌] + 원래 상품명 + 같은 카테고리 상위 트렌드 키워드 "무드"`
- 시각화: Plotly (라인 · 트리맵 · 바) + 점수 비례 워드클라우드

**발표자 스크립트**
> 분석 로직에서 제일 고민한 건 데이터랩의 정규화 방식이었습니다. 이 API는 한 번 요청할 때마다 그 안에서 가장 큰 값을 100으로 맞춰 줍니다. 그래서 요청을 나눠 보내면 요청끼리 점수를 비교할 수가 없습니다.
> 저는 카테고리마다 기준이 되는 앵커 키워드를 하나 정해서 매 요청에 같이 넣었습니다. 그러면 모든 키워드를 앵커 대비 비율로 바꿀 수 있어서 요청이 달라도 같은 척도로 비교할 수 있습니다.
> 급상승은 직전 수집 대비 점수가 15% 이상 오르거나 순위가 5계단 이상 오르면 표시합니다. 가격은 도매가에 2.2배를 하고 900원 단위로 끝나게 맞췄습니다. 39,500원짜리는 86,900원, 마진율 54.5%가 되고, 이 계산은 테스트 코드로 고정해 두었습니다.

## 8. 핵심 기술 ③: 주문 → 발주 자동화와 실시간 알림

**핵심 시각 자료**
- 시퀀스 다이어그램: 회원 주문 → 공급처별 그룹핑 → 대기 발주서 병합/생성 → Excel/PDF → 이메일·웹훅 → 상태 변경 → WebSocket
- 발주서 미리보기·PDF 캡처 (`/admin/orders?tab=po`)

**슬라이드 본문**
- 주문 접수 시 주문 상품을 **공급처별로 묶어** 해당 공급처의 '대기' 발주서에 합치거나 새로 생성
- 발주서: openpyxl(Excel) · ReportLab(한글 CID 폰트 PDF), 템플릿 표준형/간단형
- 발송: SMTP 이메일(첨부) · 웹훅(JSON) · 수동(전화·팩스)
- 상태: 대기 → 발송 완료 → 입고 확인 — 주문 상태(접수 → 발주 진행 → 발주 완료 → 입고)와 연동
- 실시간 알림: FastAPI WebSocket
  - RPA 워커 스레드에서도 `call_soon_threadsafe`로 이벤트 루프에 안전하게 전달
  - 받는 대상 분리: 주문·발주·RPA → 관리자만 / 일반 회원 → 본인 주문 상태만

**발표자 스크립트**
> 발주 자동화와 실시간 알림은 홍기흥 님이 맡았고, 저는 백엔드 쪽에서 주문 데이터 모델과 연결을 같이 설계했습니다.
> 주문이 들어오면 상품을 공급처별로 나누고, 그 공급처에 아직 보내지 않은 발주서가 있으면 거기에 합칩니다. 공급처 입장에서는 발주서를 여러 장 받는 것보다 한 장으로 받는 게 편하기 때문입니다.
> 알림에서 까다로웠던 건 스레드였습니다. RPA는 워커 스레드에서 돌고 WebSocket은 이벤트 루프에서 돌기 때문에, 스레드에서 바로 보내면 안전하지 않습니다. 그래서 `call_soon_threadsafe`로 루프에 넘기도록 했습니다. 그리고 다른 회원의 주문 정보가 새지 않도록 이벤트를 받는 사람을 권한별로 나눴습니다.

## 9. 인증 · 보안과 3단계 권한 (RBAC)

**핵심 시각 자료**
- 로그인 화면 캡처 (`/login`: 왼쪽 룩북·트렌드 TOP 10, 오른쪽 폼, 테스트 로그인 버튼 2개)
- 권한 3단계 표 + "두 겹 방어" 도식 (미들웨어 → `require_admin`)

**슬라이드 본문**
- 비밀번호: PBKDF2-SHA256 **31만 회** 반복 해시, 영문 대소문자·숫자·특수문자 8자 이상 (프런트·백엔드 동일 규칙)
- OAuth 3사 (Google · 네이버 · 카카오)
  - state = 서명된 JWT (10분 만료), 돌아갈 주소는 허용 목록 검증
  - 제공자가 **인증한 이메일**일 때만 기존 계정과 연결 (계정 탈취 방지)
- 테스트 계정 간편 로그인: 면접관이 가입 없이 바로 체험

| 권한 | 진입 | 가능 범위 |
|---|---|---|
| 일반 회원 | 가입 · 소셜 · 테스트 로그인 | 쇼핑 · 주문 · 마이페이지 |
| 실제 관리자 | `.env` `ADMIN_TOKEN` (5회 실패 시 5분 잠금) | 전체 CRUD |
| 테스트 관리자 | 테스트 관리자 로그인 버튼 | 관리자 화면 **조회만** |

- 읽기 전용 두 겹 방어: ① 미들웨어가 테스트 관리자의 모든 변경 요청을 403 ② 변경 API마다 `require_admin`

**발표자 스크립트**
> 인증과 권한은 홍기흥 님 담당이고, 저는 백엔드에서 권한 검사 구조를 같이 잡았습니다.
> 특히 말씀드리고 싶은 건 테스트 관리자입니다. 면접관분들이 관리자 화면을 바로 보실 수 있게 버튼 하나로 들어오는 계정을 만들었는데, 그 비밀번호는 공개돼 있는 셈이라 데이터를 바꿀 수 있으면 안 됩니다.
> 그래서 두 겹으로 막았습니다. 요청이 API에 닿기 전에 미들웨어가 테스트 관리자의 변경 요청을 전부 막고, 혹시 빠져나가도 각 변경 API가 실제 관리자인지 다시 확인합니다. 실제 관리자는 서버 환경 변수에 있는 토큰으로만 들어올 수 있고, 다섯 번 틀리면 5분 동안 잠깁니다.

## 10. 유저 플로우 시연

**핵심 시각 자료**
- 5컷 캡처 연결: 메인 룩북(`/`) → 상품 목록(`/shop?category=아우터`) → 상품 상세 옵션 선택(`/products/:id`) → 주문 완료 모달 → 마이페이지 주문 단계(`/mypage`) + 관리자 화면 실시간 팝업
- 라이브 데모가 가능하면 이 슬라이드에서 진행 (실패 대비 캡처 준비)

**슬라이드 본문**
- 처음 접속하면 **메인 페이지** (룩북 캐러셀 · 실시간 트렌드 · NEW ARRIVALS · TREND PICKS)
- 상품 상세: 색상을 고르면 이미지가 바뀜, 사이즈·수량 선택, 바로 구매
- 주문 즉시: 공급처별 발주서 자동 생성 → 관리자 화면에 실시간 팝업
- 마이페이지: 주문 접수 → 발주 진행 → 발주 완료 → 입고 단계 표시, 상태가 바뀌면 실시간 알림
- 공개 쇼핑몰 API에는 도매가 · 공급처 · 마진이 **나오지 않음**

**발표자 스크립트**
> 실제 흐름을 보여 드리겠습니다. 처음 들어오면 메인 페이지가 열리고, 룩북과 실시간 트렌드 키워드가 보입니다.
> 상품을 골라 색상과 사이즈를 선택하고 구매하면, 그 순간 백엔드에서 공급처별 발주서가 만들어지고 관리자 화면에는 신규 주문 팝업이 뜹니다. 회원은 마이페이지에서 주문이 어느 단계에 있는지 볼 수 있습니다.
> 백엔드 입장에서 신경 쓴 점은 쇼핑몰용 API를 따로 만든 겁니다. 관리자 API를 그대로 쓰면 도매가와 마진이 노출되기 때문에, 공개 API는 판매 등록된 상품의 판매 정보만 내려가도록 분리했습니다.

## 13. DevOps와 CI/CD

**핵심 시각 자료**
- 배포 흐름도: `git push main` → (Netlify 빌드 · Render Static 빌드 · Render Docker 빌드) + GitHub Actions(CI · Pages)
- Dockerfile 핵심 줄 발췌

**슬라이드 본문**
- **Git 연동 자동 배포**: main에 푸시하면 Netlify · Render가 각자 빌드·배포 (별도 Deploy Hook 없음)
- GitHub Actions
  - `ci.yml`: push/PR마다 **pytest 27개 케이스** + 프런트 빌드
  - `pages.yml`: `docs/**`가 바뀔 때만 GitHub Pages 배포
- Docker 이미지: python:3.11-slim, 빌드할 때 Playwright Chromium 설치, non-root 사용자 실행
- 설정 파일: `render.yaml` · `netlify.toml` · `docker-compose.yml`
- 환경 변수: `.env` 하나로 관리, `.env.example`에 **[Render 필수]** 항목 표시, 비밀값은 저장소에 넣지 않음

**발표자 스크립트**
> 배포는 박미금 조장님이 맡았습니다. main에 푸시하면 Netlify와 Render가 각자 알아서 빌드하고 배포합니다. 처음에는 GitHub Actions에서 배포 훅을 호출하는 방식도 만들었는데, 플랫폼 Git 연동과 기능이 겹쳐서 단순한 쪽으로 정리했습니다.
> Actions는 품질 확인에 집중합니다. 푸시할 때마다 pytest 27개 케이스와 프런트 빌드를 돌리고, 문서 폴더가 바뀔 때만 프로젝트 페이지를 배포합니다.
> 저는 Docker 이미지에 Playwright를 넣는 부분을 같이 작업했고, 그 과정에서 겪은 문제를 다음 장에서 말씀드리겠습니다.

## 14. 트러블슈팅 (면접 핵심)

**핵심 시각 자료**
- 3행 표: 현상 / 원인 분석 방법 / 해결 / 재발 방지
- 1번 사례는 실제 빌드 로그 캡처(`libatomic.so.1: cannot open shared object file`)를 함께 배치

**슬라이드 본문**

| 사례 | 현상 | 원인 분석 | 해결 | 재발 방지 |
|---|---|---|---|---|
| ① Render 배포 연쇄 장애 | `open Dockerfile: no such file`에 이어 `libatomic.so.1` 없음, exit 127 | 서비스 설정과 Dockerfile 위치 불일치 확인 → Playwright Node 드라이버 바이너리의 ELF 의존성(DT_NEEDED)을 직접 분석 | Dockerfile을 저장소 루트로 이동, `libatomic1`·`libstdc++6`을 Playwright 설치 전에 설치 | 필요한 라이브러리를 Dockerfile 주석으로 문서화 |
| ② 데이터랩 정규화 왜곡 | 요청을 나누면 키워드 점수끼리 비교 불가 | API가 요청마다 최댓값을 100으로 맞춘다는 점을 응답으로 확인 | 카테고리 앵커 키워드를 매 요청에 포함해 앵커 대비 비율로 환산 | 수집 모듈 docstring에 정규화 방식 기록 |
| ③ 스키마 변경 미반영 | 새 컬럼(`orders.user_id`)이 기존 DB에 생기지 않음 | `create_all`은 없는 테이블만 만들고 기존 테이블은 건드리지 않음 | 기동 시 컬럼을 확인해 추가하는 `ensure_schema` | 향후 Alembic 마이그레이션 도입 |

**발표자 스크립트**
> 세 가지를 말씀드리겠습니다.
> 첫 번째는 배포입니다. Render 빌드가 Dockerfile을 못 찾다가, 그걸 고치니 이번엔 Playwright가 라이브러리가 없다며 실패했습니다. 에러에 나온 라이브러리 하나만 넣고 다시 배포하면 또 다른 게 빠질 수 있어서, Playwright 패키지를 받아 안에 있는 Node 실행 파일이 필요로 하는 라이브러리 목록을 직접 읽었습니다. 그 결과 libatomic 말고 libstdc++도 필요하다는 걸 알고 한 번에 넣었습니다. 추측으로 여러 번 배포하는 대신 원인을 직접 확인한 사례입니다.
> 두 번째는 앞에서 설명드린 데이터랩 정규화 문제이고, 세 번째는 DB입니다. 주문에 회원 ID 컬럼을 추가했는데 이미 테이블이 있는 운영 DB에는 컬럼이 생기지 않았습니다. 지금은 기동할 때 확인해서 추가하는 가벼운 마이그레이션으로 해결했고, 다음 단계로 Alembic을 도입할 계획입니다.

**예상 질문 대비용 추가 사례 (슬라이드에는 넣지 않음)**
- **Vite 환경 변수 빌드 시점 고정** (이오리·박미금): Render 프런트가 localhost API를 호출 → 배포된 JS 번들의 문자열을 직접 확인 → 프로덕션 빌드 기본 API 주소와 CORS 기본 도메인 추가
- **읽기 전용 403이 CORS 오류로 보임** (홍기흥): 차단 미들웨어가 CORS 미들웨어 바깥에 있어 403 응답에 CORS 헤더가 없었음 → 등록 순서 조정, 회귀 테스트로 고정
- **로컬 `.env`가 운영 DB를 가리킨 사고**: 로컬 서버가 운영 TiDB에 연결됨 → 로컬·테스트는 SQLite 원칙, `AGENTS.md`에 규칙 문서화, 노출된 DB 자격증명 교체 [확인 필요 — 교체 완료 여부]

## 16. 회고와 향후 고도화

**핵심 시각 자료**
- 왼쪽: 배운 점 3개 / 오른쪽: 로드맵 (단기 · 중기 · 장기)

**슬라이드 본문**
- 배운 점
  - 무료 인프라 제약(단일 인스턴스, 휘발성 디스크)이 설계를 결정한다
  - 에러 메시지를 고치기보다 원인을 직접 확인하는 것이 배포 횟수를 줄인다
  - 테스트와 운영 환경 분리는 규칙으로 문서화해야 지켜진다
- 향후 계획
  - **단기:** Alembic 마이그레이션, 실제 공급처 어댑터(도매꾹 Open API 등)
  - **중기:** S3/R2 이미지 저장소, Celery/Redis 작업 큐로 RPA 워커 분리
  - **장기:** LLM 기반 상품 설명·키워드 군집화, 결제(PG) 연동, AWS 이관

**발표자 스크립트**
> 회고입니다. 가장 크게 배운 건 인프라 제약이 설계를 정한다는 점이었습니다. 무료 티어는 인스턴스가 하나이고 디스크가 재배포 때 지워지기 때문에, 스케줄러를 API 안에 두었고 이미지 저장은 아직 임시로 남아 있습니다.
> 그래서 다음 단계는 분명합니다. 먼저 Alembic으로 마이그레이션을 정식화하고, 이미지는 S3 같은 외부 저장소로 옮기고, RPA는 Celery와 Redis로 별도 워커로 분리하려고 합니다. 그 위에 LLM으로 상품 설명을 만들고 키워드를 묶는 기능까지 확장하는 것이 목표입니다.
